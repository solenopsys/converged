# Ядро на Zig + бизнес-логика провайдеров в JS

План перевода вендорной логики LLM-провайдеров из Zig-модулей в загружаемые
JS-дескрипторы.

Статус: этапы 1–5 сделаны для чат-провайдеров. Вендорных Zig-модулей на этой оси
не осталось. Ось голосовой сигнализации (`signaling/*`, SDP) не тронута — см.
раздел 10.

## 1. Концепция

Ядро на Zig даёт механизмы, JS-модули — политику.

Ядро развивается, но по одному правилу: когда у нового провайдера обнаруживается
специфика, **обобщается существующий примитив ядра**, а не добавляется кастомный
Zig-плагин под вендора. Выигрыш не в том, что ядро заморожено, а в том, что оно
меняется редко и в предсказуемую сторону, оставаясь стабильным API, поверх
которого скрипты дорабатываются свободно.

Прецедент в коде уже есть: политика звонка (`policy/engine.zig`) исполняется в
QuickJS и возвращает типизированный план. Та же схема распространяется на
провайдеров.

### Вендорная специфика в `openai_realtime.zig`

Из 667 строк специфика OpenAI сосредоточена в пяти местах, все внутри `Session`:

| Строка | Что | Куда уходит |
| --- | --- | --- |
| 371 | `"{s}?model={s}"` | конфиг |
| 375 | `Authorization: Bearer {key}` | конфиг |
| 380 | `ldc_create_websocket_with_header` | выбор транспорта |

ни одного упоминания вендора. Это generic-менеджер ресурсов, написанный внутри
вендорного файла. ~260 строк, переиспользуемых как есть.

## 3. Целевая архитектура

### Дескриптор провайдера (JS)

```js
export const openaiRealtime = {
  apiVersion: 1,
  transport: "ws",
  stateful: true,
  url:     (cfg, model) => `${cfg.baseUrl}?model=${model}`,
  headers: () => ({ Authorization: "Bearer ${secret:openai}" }),
  handshake: [
    { await: "session.created", timeoutMs: 10000 },
    { send:  (cfg) => sessionUpdate(cfg) },
    { await: "session.updated", timeoutMs: 10000 },
  ],
  fatal:       (ev) => ev.type === "error",
  encodeTurn:  (req) => responseCreate(req),
  decodeEvent: (raw, st) => [ /* нормализованные события */ ],
};
```

Хендшейк — данные, а не код ядра. Zig исполняет шаги, JS их описывает. Это 3–4
вызова JS на создание сокета; сокеты создаются раз в сессию, стоимость нулевая
по построению.

Побочный эффект: исчезает `bisect_skip_session_update` (строка 411) — отладочный
флаг, вкомпилированный в бинарь ради проверки гипотезы про `session.update`.
С дескриптором такая проверка становится правкой строки в скрипте.

### Транспорт

Пулу от транспорта нужно ровно пять операций:

```
open(url, headers) -> conn     // асинхронно, может упасть или таймаутнуть
alive(conn) -> bool
send(conn, bytes)
recv -> поток кадров           // сейчас: messageCallback на нативном треде
close(conn)
```

WS ложится 1:1. HTTP/2-стрим, SSE-over-POST, raw TCP — за тем же vtable. Пул не
знает, что под ним.

### Пул

Generic, конфигурируется `idle`, `stateful`, таймаутами. Сохраняет аффинность
сессии, single-flight рефилл, вытеснение мёртвых, ретрай.

Флаг `stateful` обязателен и выносится в дескриптор: `active`-мапа по
`session_id` существует потому, что вендор держит состояние разговора на сокете.
Для stateless-провайдера тот же пул вырождается в пул соединений, где выдать
другое соединение той же сессии законно. Без явного флага абстракция протекает.

### Стабильная поверхность ядра

- дескриптор: `apiVersion`, `transport`, `stateful`, `url()`, `headers()`,
  `handshake[]`, `fatal()`, `encodeTurn()`, `decodeEvent()`
- транспорты за одним vtable, дескриптор только называет нужный
- generic-пул
- `__host` — обратный канал JS → Zig, уже есть в обёртке

Прирастать поверхность будет списком транспортов и видами шагов хендшейка.

## 4. Правила, удерживающие концепцию

**Правило обобщения.** Новый примитив ядра принимается, только если он осмысленно
описывает минимум двух провайдеров. `{await: <тип события>}` описывает любого, у
кого хендшейк на событиях; `waitSessionCreated()` — одного. Второе формально тоже
«ядро, а не плагин», но это вендор, просочившийся в API.

**Греп-инвариант (в CI).**

```
grep -rn '"openai"\|"claude"\|"gemini"\|"anthropic"' src/ --include=*.zig
```

Пусто везде, кроме разбора конфига. Сегодня падает в первую очередь на
`hub.zig:resolve()` — цепочке `std.mem.eql(u8, name, "openai")` … `"claude"` …
`"gemini"`, то есть диспетчере по имени вендора внутри ядра. После перехода на
дескрипторы функция исчезает: имя провайдера становится ключом в таблице
загруженных модулей.

**Версия контракта.** Дескриптор объявляет `apiVersion`; ядро отказывается
грузить незнакомую — громко и на старте. Режим тот же, что у
`LLM_GATE_POLICY_REQUIRED=true`: падать, а не работать в обход сломанного
скрипта. Схема дескриптора валидируется строго, как `policy/types.zig` валидирует
план звонка, — иначе опечатка в JS превращается в 400 от вендора в проде вместо
отказа при загрузке.

## 5. Что не делегируется

**Scope.** README: «It does not derive a tenant or `scope` from the payload: a
missing scope is refused». Если JS может вернуть или переписать scope — свойство
исчезает. Дескриптор его не видит.

**Ключи.** Дескриптор возвращает `"Bearer ${secret:openai}"`, подстановку делает
Zig перед отправкой. Ключ не пересекает песочницу. Песочница QuickJS сетей не
имеет, но `__host` — имеет, и это единственный канал наружу.

**Медиаплоскость.** RTP/Opus/WebRTC/SIP, `bridge/openai_bridge.zig`. JS туда не
заходит ни в одном варианте: 50 кадров/с на звонок.

## 6. Ограничение по конкурентности

`JSRuntime` не потокобезопасен, а `messageCallback` (строка 384) вызывается на
нативных тредах libdatachannel — свой на сокет. Общий мьютекс на рантайм
сериализует все сессии сразу.

Решение: по `JSRuntime` на воркер-тред пула, декод сокета всегда на владеющем им
треде. QuickJS допускает сколько угодно независимых рантаймов; шаринг объектов
между ними не нужен, состояние дескриптора — по сессии.

## 7. Стоимость вызова

Горячий путь JS не вызывает вообще. Ядро разбирает событие один раз своим
`std.json`, ищет тип в таблице и копирует поля по путям. Ни второго разбора, ни
пересечения ABI.

Первая версия схемы делала дескриптор набором функций, вызываемых на событие.
Это давало `JSON.parse` в JS → `JSON.stringify` в JS → `JSON.parse` в Zig: три
разбора там, где нужен один. Схема заменена на таблицу-данные.

JS остаётся только на тёплом пути, где частота — десятки вызовов, а не тысячи:

| Точка | Частота | JS |
| --- | --- | --- |
| policy `onIncomingCall` | 1 / звонок | да |
| `sessionConfig` (шаг хендшейка) | 1 / сокет | да |
| `encodeTurn` | 1 / ход | да |
| `decodeResponse` / `decodeDone` | 1 / ход | да |
| `decodeEvent` | ~30–100 событий/с × N потоков | **нет, таблица в Zig** |
| аудиокадр | 50/с × N звонков | никогда |

Замер персистентного рантайма (x86_64/ReleaseFast, один тред): пустой вызов
79 нс, эхо аргумента 94 нс. Для тёплого пути с запасом в тысячи раз.

## 8. Этапы

### Этап 1 — ABI обёртки qjs — сделано

`core/native/wrappers/rt/qjs/src/main.zig`, `test/run_lib.zig`, `README.md`;
`resonus/src/native/qjs_client.zig`.

Было: `qjs_eval` создавал `JS_NewRuntime()` и освобождал его на каждом вызове,
а `policy/engine.zig` конкатенировал скрипт с обёрткой и компилировал заново.
Для решения раз в звонок нормально, для вызова на событие — нет.

Добавлено к ABI, `qjs_eval` сохранён без изменений:

- `qjs_rt_new` / `qjs_rt_free` — рантайм с собственными `JSRuntime` + `JSContext`;
- `qjs_rt_load` — загрузка скрипта один раз, определения живут в `globalThis`;
- `qjs_rt_compile` / `qjs_rt_load_bytecode` — компиляция в байткод и загрузка его
  в любой рантайм этой же сборки;
- `qjs_rt_call` — `globalThis[name](arg)`, аргумент и результат — непрозрачный
  UTF-8, JSON остаётся на стороне скрипта;
- `qjs_rt_has_fn` — проверка формы модуля при загрузке, а не на первом событии;
- `qjs_rt_set_host_fn` — `__host` на рантайм, с opaque-указателем;
  process-global вариант остался только для `qjs_eval`;
- `qjs_rt_set_timeout_ms` — бюджет на вызов, взводится на входе в каждый вызов,
  так что долгоживущий рантайм не накапливает потраченное время.

Тредовая аффинность — контракт, а не блокировка: рантайм принадлежит одному
треду на всю жизнь, конкурентность даётся рантаймом на воркер. Debug-сборки
проверяют вызывающий тред, release — доверяют. `qjs_client.zig` получил
`Runtime` рядом с существующим `Client`; `Client` с его process-global мьютексом
для этого не годится — он бы согнал все сессии в один лок.

Покрыто тестами (`zig build test`): сохранение состояния между вызовами,
исключение, отсутствующая функция, `has_fn`, прерывание по таймауту с
последующим повторным использованием рантайма, `__host` на рантайм с разными
user-указателями, изоляция глобалов между рантаймами, roundtrip байткода между
рантаймами. Плюс замер из раздела 7.

Регрессий нет: `policy/engine.zig` не тронут, тесты resonus — 23/23.

### Этап 2 — TS-модуль и сборщик — сделано

`core/native/apps/resonus/providers/` — bun-пакет в workspace монорепы.

- `src/schema.ts` — контракт дескриптора: пути, эмиты, `when`/`cases`, `each`,
  escape-hatch на хук, транспорт, хендшейк.
- `src/validate.ts` — валидация на сборке: неизвестный эмит, кривой путь,
  неотмеченный `stateful`, хук без реализации, лишнее поле у эмита.
- `src/build.ts` — сборщик: `dist/<name>.table.json` (данные),
  `dist/hooks.js` (один IIFE со всеми хуками), `dist/manifest.json` с sha256.
- `src/core.ts` — общая для всех вендоров логика: склейка system-сообщений,
  сборка унифицированного ответа, пустая схема инструмента, разбор присланного
  вендором текста аргументов.
- `src/providers/<name>.ts` — дескриптор, `<name>.hooks.ts` — логика.

`encodeTool` и `encodeMessage` намеренно оставлены по провайдерам: они
различаются у всех, и унификация означала бы общую функцию с ветвлением по
вызывающему — та же связанность, ради снятия которой всё и делается, только
менее заметная.

Дескриптор и хуки разнесены по файлам намеренно: entry бандла импортирует только
`*.hooks.ts`, поэтому транспорт и таблица физически не могут попасть в скрипт для
движка. Это свойство даёт раскладка файлов, а не tree-shaking бандлера. Хук-файлы
импортируют только типы. Бандл — 11 КБ на четыре провайдера, ноль данных таблиц.

Перенесены: `anthropic`, `openai`, `openai-realtime`, `gemini`.

### Этап 3 — ядро исполняет таблицы — сделано

- `src/llm/descriptor.zig` — загрузчик: разбор таблицы в исполняемый вид, пути
  предварительно разрезаны на сегменты, события отсортированы под бинарный
  поиск, `apiVersion` сверяется, `stateful` обязателен.
- `src/llm/decode.zig` — исполнитель: разрешение путей, `when`/`cases`, `each`,
  списки правил, накопление состояния хода (текст, tool-call'ы по ключу
  корреляции, usage, finish), escape-hatch через инжектируемый `HookRunner`.

Ключ корреляции tool-call'а приводится к строке независимо от типа: у Anthropic
это целый `index`, у OpenAI Realtime — строковый `call_id`, накопителю всё равно.

Тесты (8, в `zig build test`, всего 31/31) гоняют настоящие эмитированные
таблицы через реальные последовательности событий трёх вендоров: текст плюс
tool-call с двумя фрагментами аргументов, SSE-строки без payload, `error`,
sentinel `[DONE]`, WS-кадры без префикса, терминальный хук, неизвестный тип
события, отказ по версии контракта, отказ по отсутствующему `stateful`.

Таблицы подключены в тестовый бинарь через `addAnonymousImport` — только в
тесты. Работающий гейт читает их с диска, иначе теряется смысл всей затеи.

Отдельно: `providers/src/qjs.test.ts` прогоняет собранный бандл через настоящую
`libqjs.so` по `bun:ffi` — 10 тестов на хуки всех четырёх провайдеров.
Типизация доказывает, что хуки компилируются; это доказывает, что они
исполняются в том движке, который их и будет исполнять.

### Этап 4 — снять старые адаптеры — сделано

Удалены `llm/claude.zig`, `llm/openai.zig`, `llm/gemini.zig`,
`llm/openai_realtime/protocol.zig`. Добавлены:

- `llm/registry.zig` — загрузка `manifest.json`, таблиц и `hooks.js`; пул
  QuickJS-рантаймов для тёплых хуков; подстановка `${secret:...}`, `${env:...}`,
  `${env:NAME:default}`, `${model}`. Секрет резолвится в Zig и в песочницу не
  попадает.
- `llm/engine.zig` — generic-провайдер поверх HTTP: `encodeTurn` хуком, ответ
  через таблицу (стрим) или `decodeResponse` (не-стрим). То, чем были три
  адаптера, минус три копии одного управляющего потока.
- `llm/hub.zig` переписан: диспетча по имени вендора нет, `resolve()` больше не
  существует. Провайдер ищется в реестре по имени, которое объявил дескриптор.
  `endpoint()` читает `RESONUS_ENDPOINT_<NAME>` вида `<провайдер>:<модель>`.
- `signal_provider.zig:defaultModel` — была таблица вендорных дефолтов в коде,
  стала `RESONUS_MODEL_<PROVIDER>` с фолбэком `AI_MODEL`.

### Этап 5 — расщепление realtime — сделано

`llm/openai_realtime.zig` → `llm/ws_pool.zig`: session-affine пул для любого
провайдера со stateful-транспортом. URL, заголовок авторизации, хендшейк и
грамматика событий приходят из дескриптора; полезная нагрузка хода — из хука
`encodeTurn`. В файле осталось то, что про сокеты и треды: жизненный цикл
соединения, лизинг, single-flight рефилл, вытеснение мёртвых, ретрай.

Заодно исчез `bisect_skip_session_update` — отладочный флаг, вкомпилированный в
бинарь; хендшейк теперь строка в дескрипторе.

Понадобился один новый примитив ядра — `turn.end`. Сессионный транспорт держит
соединение между ходами, и что-то должно сказать, где ход кончился: HTTP-тело
заканчивается само, вебсокет — нет. Примитив принят по правилу из раздела 4: он
описывает любой сессионный транспорт, а не особенность OpenAI.

## 9. Критерий готовности

Достигнут для чат-провайдеров: новый провайдер добавляется одним TS-файлом
дескриптора, одним файлом хуков и строкой конфига. Пересборка Zig не нужна.

Греп-инвариант по `src/**/*.zig`, кроме тестовых фикстур:

```
src/policy/engine.zig:80      default provider в JS-обёртке gateway.ai()
src/sip/sip_server.zig:755    media executor поддерживает одного провайдера
src/gate/gateway.zig:585,613  то же
```

Все четыре — ось голосовой сигнализации, не чата. По `src/llm/` инвариант чист.

## 10. Ось голосовой сигнализации — не сделана

`signaling/openai.zig` (573 строки) и `signaling/gemini.zig` (77) остаются
вендорными модулями. Это другая ось: согласование SDP для WebRTC-звонка,
multipart-тело к `/v1/realtime/calls`, конфиг транскрипции. Схема дескриптора её
не моделирует вообще — там нет ни SDP, ни multipart, ни `ai()`-плана звонка.

Оставшиеся четыре совпадения греп-инварианта отсюда же: медиа-исполнитель
поддерживает одного провайдера, что README и фиксирует. Снять проверку имени, не
реализовав второго провайдера, значит просто передвинуть отказ вглубь.

Это отдельная работа со своей схемой дескриптора, не продолжение этой.

## 11. Открытые вопросы

- Границы `decodeEvent`: отдавать в JS каждый кадр или нарезанный батч.
- Формат состояния между вызовами `decodeEvent` (аккумуляция tool-call
  аргументов): держать в JS или прокидывать через ядро.
- Cruller (`core/native/wrappers/rt/cruller`) как альтернативный хост: JSC с JIT,
